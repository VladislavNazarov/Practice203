# Стратегия контейнеризации

## 1. Выбор базового образа

Для контейнеризации выбран образ `python:3.11-slim`.

Причины выбора:
- образ заметно меньше полноценного `python:3.11`, но при этом совместим с обычными Python-пакетами без дополнительных сложностей Alpine;
- Debian-based runtime проще для отладки и повторяемого CI;
- образ позволяет безопасно запускать приложение от отдельного непривилегированного пользователя;
- стек проекта минимален (`fastapi`, `uvicorn`, `pydantic`), поэтому slim-образ дает хороший компромисс между размером и совместимостью.

В `Dockerfile` используется `multi-stage build`:
- `builder` устанавливает только runtime-зависимости в отдельное virtualenv;
- `runtime` получает готовое окружение и каталог `app/`, без тестов, git-метаданных и dev-инструментов.

## 2. Управление ENV

| Переменная | Назначение | Пример значения в Compose |
| --- | --- | --- |
| `APP_ENV` | Режим запуска приложения | `production` |
| `APP_HOST` | Хост для `uvicorn` внутри контейнера | `0.0.0.0` |
| `APP_PORT` | Порт приложения внутри контейнера | `8000` |
| `SECRET_KEY` | Секрет приложения | `local-compose-secret` |
| `DATABASE_URL` | Строка подключения к БД | `postgresql://videohosting:videohosting@db:5432/videohosting` |
| `REDIS_URL` | Адрес Redis | `redis://cache:6379/0` |
| `UPLOAD_DIR` | Каталог загрузок внутри контейнера | `/app/uploads` |
| `MAX_VIDEO_SIZE_MB` | Ограничение размера загружаемого файла | `500` |
| `POSTGRES_DB` | Имя базы данных для контейнера PostgreSQL | `videohosting` |
| `POSTGRES_USER` | Пользователь PostgreSQL | `videohosting` |
| `POSTGRES_PASSWORD` | Пароль PostgreSQL | `videohosting` |

Принцип: параметры сети и учетные данные вынесены в ENV, чтобы один и тот же compose-сценарий можно было переносить между локальной машиной, CI и другим хостом без переписывания конфигурации.

## 3. Оптимизация образа

Примененные оптимизации:
- отделены runtime-зависимости в `requirements-runtime.txt`, чтобы не переносить в production `pytest`, `black`, `flake8`, `bandit`, `detect-secrets` и `pre-commit`;
- порядок слоев оптимизирован под Docker cache: сначала зависимости, затем код приложения;
- в runtime-слой не попадают `tests/`, `.git`, IDE-файлы и локальные кэши благодаря `.dockerignore`;
- приложение запускается от пользователя `app`, а не от `root`.

Сравнение образов:
- до оптимизации: одностадийный образ на `python:3.11` с установкой полного `requirements.txt`;
- после оптимизации: многоэтапный образ на `python:3.11-slim` с установкой только `requirements-runtime.txt`.

Фактические размеры должны фиксироваться после первой локальной сборки или CI-сборки, потому что в момент подготовки артефактов Docker daemon на машине не был доступен. Ожидаемый результат - заметное уменьшение образа за счет slim-базы и исключения dev-зависимостей.

## 4. Вывод

Контейнеризация проекта делает окружение воспроизводимым:
- приложение собирается одинаково локально и в GitHub Actions;
- `db` и `cache` поднимаются рядом с приложением в единой сети Docker;
- публикация образа в GHCR после успешных тестов позволяет запускать одинаковый runtime-артефакт на любой машине.
